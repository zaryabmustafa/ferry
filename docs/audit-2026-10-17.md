## Security

### S1 · Medium-High · CONFIRMED (no exploit built): the server's identity is never checked
Ferry decides where it is from two things (`location.rs:143-166`, `net.rs:236`):
- the gateway's MAC address, taken from ARP and not authenticated;
- TCP port 445 being open at the remembered LAN IP.

It then signs in over SMB to a bare IP (`job.rs:322`). With a bare IP, Windows uses NTLM, not Kerberos.

An attacker on a network the laptop joins can copy the home router's MAC (a stock router setting) and answer on the server's IP. A rogue SMB server can also accept any sign-in. Ferry then:
- **sends the NTLMv2 response**, which can be cracked offline or relayed;
- **during an unload, uploads the carried source data to the attacker**;
- **posing as the source, receives files that are later pushed into the real destination backup**, overwriting good copies. Fake deletes are only limited by the 10% / 50-file thresholds.

The attack is targeted: the attacker must know the MAC and the IP. Shared VRRP/HSRP virtual MACs (`00:00:5e:00:01:xx`) can also collide by accident between unrelated networks.

The README's threat model does not mention any of this.

**Fix:** pin the server's identity at "Remember this network". Options:
- the SMB server GUID;
- a random token file written to the share and checked before each trip;
- at minimum, requiring SMB signing.

Document the risk.

### U1 · High · CONFIRMED: auto-update trusts whoever controls the release server
The auto-update branch downloads `Ferry-Setup-X.Y.Z.exe` and `SHA256SUMS.txt` from the same release, then runs the installer silently (`/S`) in the background on every installed copy, about once a day. Nothing is signed.

The trust boundary is therefore the release server, the owner's account on it, and the CI token that publishes releases. Compromising any one of them means code runs on every installed Ferry with no prompt.

What is done well:
- downgrades are refused (`is_newer`);
- downloads are size-capped;
- a failed install is skipped rather than retried;
- portable copies never update themselves;
- the update can be switched off.

**Fix:** sign `SHA256SUMS.txt` in CI with a key kept outside the release server (for example ECDSA P-256 or minisign), embed the public key in `ferry.exe`, and refuse any update whose signature doesn't verify. Until then, the README says plainly that publishing a release is the same as shipping code to every install.

### U2 · Medium · CONFIRMED (**fixed**): update links weren't pinned to https
`http.rs` used plain HTTP for any `http://` link. The installer and checksum links came from the release JSON unchecked. An `http://` link, which a misconfigured server's root URL would produce, would let anyone on the network swap both files.

### S2 · Medium (high impact, exploitability unproven) · CONFIRMED missing check: file names from the server are never validated
Names come straight from `read_dir` (`entry.rs:50`) and are joined as strings (`diff.rs:36`), then with `Path::join` in these places:
- `fill.rs:89, 131, 173, 207`
- `unload.rs:87, 99, 217, 246`
- `trip/mod.rs:261, 272`

Nothing rejects `..`, `:`, a leading `\`, or an absolute name. `Path::join` *replaces* the base path when the name is absolute. So if a hostile or compromised server can get a name like `C:\Users\…\Startup\x.exe` or `\x` through the Windows SMB client:
- the fill writes outside the cargo folder;
- the delete path removes files outside the pair root.

Whether the Windows redirector passes such names through was not tested.

**Fix:** one `safe_rel()` helper that every join goes through. Reject separators, `:`, NUL or control characters, and `.` and `..`, and assert that every path component is a normal one. This is cheap defence in depth; do it regardless.

### S3 · Low-Medium · CONFIRMED (**fixed**): the owner's real infrastructure is committed to a repo meant to go open source
A design spec named the owner's server names, LAN subnets and server IP, Wi-Fi SSIDs and Tailscale subnet-route setup.

This is useful reconnaissance. Scrub it, and if the repo is or will be public, rewrite the history. (Done: the values were replaced, and the public repository starts from a clean history without them.)

### S4 · Low · CONFIRMED: release supply chain
- The binaries and the installer are **not Authenticode-signed**. SmartScreen will warn, and nothing ties a binary to its author.
- `SHA256SUMS.txt` is published on the same server as the binaries, so it protects against corrupted downloads, not against a compromised server. Fix: sign the sums (minisign or GPG), or sign the binaries.
- CI actions are pinned to tags (`@v4`), not commit SHAs, and `upload-artifact@v3` / `download-artifact@v3` are deprecated.

### S5 · Low · CONFIRMED: `ERROR_SESSION_CREDENTIAL_CONFLICT` counts as success (`smb.rs:94`)
If Explorer already has a session open to that server as a different user, two things go wrong:
- "Test connection" reports OK without testing the credentials that were entered;
- trips run as the other identity.

### S6 · Info: hardening notes
- The pipe accepts `SaveCredential` for **any** credential target (`engine.rs:698`), so any process running as the same user could overwrite, say, a `git:` credential through Ferry. That process could already do this directly, so it does not cross a security boundary. Still, restrict targets to the `Ferry/` prefix.
- Password wiping is partial. The IPC line buffer, the serde `String` and the Slint text are never zeroed, so `wipe()` gives a false sense of hygiene.
- The pipe name `\\.\pipe\ferry` is machine-wide. Another local user can claim it first and stop your engine from starting (a DoS). The client-side SID check (`ipc.rs:158`) correctly prevents the password from leaking.
- The portable zip does not call `SetDefaultDllDirectories`. If it is run from Downloads, the usual DLL-planting caveat applies.
- The carried data on the laptop is unencrypted. The README says so and recommends BitLocker, which is good.

### What's done well (security)
- **Named pipe:**
  - the DACL allows only the current user's SID;
  - `FILE_FLAG_FIRST_PIPE_INSTANCE` stops another process from claiming the name;
  - `PIPE_REJECT_REMOTE_CLIENTS`;
  - requests are capped at 64 KiB and oversize ones are drained;
  - at most 8 connections at once;
  - the **client checks that the pipe server runs as the same user before it sends a password** (`ipc_server.rs:61-97`, `ipc.rs:158-166`, `sid.rs`).
- Passwords live only in Credential Manager (DPAPI). A hand-written `Debug` for `Request` keeps them out of logs, and a test checks it (`ipc.rs:38-62, 284`).
- No listening network ports and no telemetry. At 560a7c7 there was no download-and-execute anywhere; the auto-update branch adds one (U1).
- The installer is per-user, with no elevation.
- The Tailscale checker **fails closed**: a timeout, odd output or a relay means no copy (`tailscale.rs:40-71`).
- Bulk copies happen only after a fresh location check at the start of the trip, a route check before each file, and a full re-check every 30 s (`job.rs:246-274`).

## Data safety (the part skeptics should care about most)

No code path deletes a destination file while bypassing `decide()`, the function that applies the thresholds and refuses after an empty, partial or failed listing. **Verify-before-replace is real:**
1. Write to `.ferry-part`.
2. Read it back unbuffered.
3. Compare the hash.
4. Swap it in with `MoveFileExW(REPLACE_EXISTING | WRITE_THROUGH)`, with no copy fallback (`copy.rs:173-194`, `unload.rs:246-269`).

State files are written as temp file → `sync_all` → rename, and a corrupt state file is moved aside (`cargo.rs:35-70`).

The gaps:

| # | Severity | Finding | Where |
|---|---|---|---|
| D1 | **Medium** · CONFIRMED | **Resumed copies hash the laptop's partial file, not the source.** The part already on the laptop is re-hashed from disk (`copy.rs:102`), and that hash becomes the "source hash" the unload checks against. If the laptop bytes were damaged, or the source changed in place with the same size and mtime, corrupt data is delivered and marked "verified". The README's "compared with the hash taken at the source" is false for resumed files. | `copy.rs:96-105`, `fill.rs:22-24` |
| D2 | **Medium** · CONFIRMED | **Source files are opened with full sharing** (Rust's default: READ, WRITE and DELETE). A VHDX, database or PST that is being written in place can be copied torn. NTFS doesn't update the mtime on every write, so the 10-minute "stable" rule and the size check after the copy can miss it. Fix: open the source with read-only sharing, so a file still held by a writer fails as "locked" and is retried later. | `copy.rs:45-50` |
| D3 | **Medium** · CONFIRMED | **Overlapping destinations are allowed.** Pair A → `backups` and pair B → `backups/vm`: A sees B's files as "extra at the destination" and queues them for deletion. Below the thresholds this happens silently, and the cycle repeats every trip. Setup only rejects duplicate *source* paths. | `setup.rs:234` |
| D4 | Medium · SUSPECTED | Listings that hide files without an error (Access-Based Enumeration, Samba `hide unreadable`, veto files) make those files look deleted. Only the thresholds stop the deletes. | `diff.rs:162-171` |
| D5 | Low · CONFIRMED | An oversize, permanently locked or non-Unicode file name (`to_string_lossy`) holds that pair's deletes forever, with no message saying why. | `fill.rs:112,186`, `entry.rs:50` |
| D6 | Low · CONFIRMED | Confirming deletes while no trip is running checks only the count. If a fill ran in between, a *different* set of the same size is approved. | `engine.rs:1133` |
| D7 | Low · SUSPECTED | Rust's `to_lowercase` does not match Windows case folding (ς/σ, ſ, ı, the Kelvin sign). A case-sensitive source holding both `A.txt` and `a.txt` collides in the cargo folder. | `diff.rs:47`, `cargo.rs:106` |
| D8 | Low · CONFIRMED | A negative or zero mtime makes `now - mtime` overflow in release builds. The file then counts as "unstable" forever, and `finalize` fails for FILETIME 0. | `entry.rs:32`, `diff.rs:33,235` |
| D9 | Low · CONFIRMED | Orphaned `.ferry-part` files on the destination are never cleaned up (multi-GB leaks are possible). A real user file named `*.ferry-part` is never mirrored and can be deleted. | `entry.rs:51`, `unload.rs:249` |
| D10 | Low (performance) | The whole manifest is rewritten and fsynced 2× per carried file, with linear scans. That is O(n²) for 100k small files. | `fill.rs:216,232`, `cargo.rs:103` |
| D11 | Low | The single-instance mutex is `Local\` (per session), so a console session and an RDP session can run two engines on the same state files. | `win/mod.rs:17` |

**Done well:**
- **The crate split:** pure logic lives in `ferry-core`, and CI checks that it doesn't depend on a UI toolkit.
- **The process model:** the engine runs on a single thread, blocking work goes to worker threads, and the UI runs in its own process.
- **Injectable seams make location logic testable:** `locate()` takes the probe and route closures as parameters, which allows 28 scenario tests.
- **The copy pipeline:** unbuffered and write-through, with double buffering and resume.
- **Correct tray message-loop details:** re-entrancy, restarts of Explorer, and the `SetForegroundWindow`/`WM_NULL` popup pattern.
- **Real accessibility work:** roles, labels and values, focus rings that appear only for keyboard use, high-contrast colours, and accent colours adjusted for WCAG contrast (with tests).
- **Comments explain *why*, not *what*.**

## What to fix first

1. **S2 + D3:** add `safe_rel()` on every join, and reject overlapping destination roots. These are small diffs, and they close the worst possible outcomes (writes or deletes outside the intended folders).
2. **D1 + D2:** on resume, re-read the already-copied part from the source; open source files with read-only sharing. Together these make the claim that "verified" means *the source's bytes* true.
3. **CI:** run the tests, and make sure the binary that ships is the one that was tested (same toolchain).
4. **Run the drills in `docs/verification.md`** on real servers before calling it safe for anyone else's backups. Publish the results.
5. **S1:** pin the server identity, or at least document the spoofing risk in the README's safety section.
6. **S3:** scrub the private infrastructure details before the repo goes public. **S4:** sign the releases or the checksums.
